# Per-layer test coverage audit

Answers the owner's question — *"czy mamy pełne pokrycie testami każdego poziomu?"*
("do we have full test coverage of every layer?") — with numbers, a
risk-ranked gap list, and a ratchet that stops any layer from silently
regressing.

## How to read / reproduce

```bash
cd app
npm run coverage        # runs vitest with v8 coverage, prints the table, enforces the floor
npm run coverage:check  # report-only ratchet gate (used by npm run coverage)
npm run coverage:baseline  # re-measure and rewrite coverage-baseline.json floors
```

- Provider: `@vitest/coverage-v8` with `all: true`, so **every** source file in
  the include globs counts — files never touched by a test show up as 0%, not
  as absent. This is deliberate: it makes the honest denominator visible.
- Measured surface: `core/**`, `adapters/**`, `apps/**`, `scripts/**`.
  Excluded: test files, Storybook stories, `.d.ts`, web test harness,
  snapshot fixtures, the coverage tooling itself, and the dev-only data scripts
  `adapters/db/{seed,reseed,migrate}.ts` (run by `db:*` and exercised by
  `smoke`, not port implementations).
- The table below is regenerated by `scripts/coverage-report.ts` between the
  markers; do not hand-edit it.

### Targets and ratchet policy

| Layer | Target |
| --- | --- |
| core/domain, core/contract, core/client | > 85% lines, > 80% branches (met) |
| core/server | > 85% lines (met), > 80% branches (76.9% measured; 76% ratchet floor) |
| adapters | > 70% lines |
| apps/web, apps/cli, apps/server, scripts | reported, ratcheted, not gated to a fixed target |

`apps/*` and `scripts/*` are driven mostly by the runtime gates
(`smoke`, `e2e:*`) rather than vitest, so their unit numbers understate real
coverage — see "What the unit numbers miss" below.

### Verdict

**No — coverage was not uniformly "full", and now it is measured, honest, and
ratcheted.** The single-worker measurement re-bases every floor to the achieved
value rounded down. All four core layers exceed **85% lines**, and adapters clear
**70% lines** at 75.2%. Core/server branches are **76.9%**, 3.1 points below the
stated **>80%** target, so its honest ratchet floor is now 76% while >80% remains
the restoration target; the other core branch results clear that target.
The high-risk surfaces the owner cares about — money/price math, entitlement
edges, tenant isolation, auth/secret crypto, webhook transitions, error-code
mapping, CLI exit codes — are covered by unit tests (new or pre-existing) plus
the smoke/e2e runtime gates. `apps/cli`, `apps/server` and `scripts` stay low on
*unit* coverage by design: they are thin wiring/tooling exercised by `smoke` and
the `e2e:*` scripts, not by vitest.

## What the unit numbers miss (E2E / runtime coverage)

Unit coverage is measured only from `vitest`. Several critical paths are
covered instead — or in addition — by runtime gates that vitest does not
observe, so a low unit number on those files is **not** an untested path:

- **`npm run smoke`** (`scripts/smoke.ts`): boots the real server on an
  ephemeral port and drives health → sign-in → product list → simulated
  purchase → magic-link sign-in through the CLI, asserting taxonomy exit codes
  (including `unauthorized = 3`). This exercises `apps/server`, `apps/cli`,
  `core/client/http.ts`, and the DB repositories end to end.
- **`npm run e2e:auth`** (`scripts/auth-e2e.ts`): passkey / TOTP / password
  reset / magic-link auth flows against `adapters/auth/*`.
- **`npm run e2e:poc`** (`scripts/poc-e2e.ts`): creator + member happy path
  across products, courses, grants, entitlements.
- **`npm run e2e:subs`** (`scripts/subs-e2e.ts`): full subscription lifecycle
  (checkout → invoice.paid renewal → payment_failed → cancel) through the real
  Stripe-shaped webhook path.
- **Adapter integration tests** (`adapters/db/importer.test.ts`,
  `post-search.test.ts`, `adapters/auth/create-auth.test.ts`) spin up isolated
  Postgres databases and exercise `repositories.ts` / importer / auth against
  real SQL — coverage that only materializes when those DB-backed tests run.

The consequence: `core/client/http.ts` (thin per-endpoint wrappers) and
`adapters/db/repositories.ts` (SQL) carry meaningful risk that is validated by
smoke/e2e, and the unit percentage for those files should be read with that in
mind. Where a unit test could add real assurance cheaply, this audit added one;
where only an integration/e2e test can meaningfully exercise the code, the gap
is called out rather than papered over with a shallow unit test.

### Residual gaps (accepted, with rationale)

- **`core/client/http.ts`** — ~80 thin per-endpoint wrappers over one shared,
  well-tested `request` helper (`http.test.ts` covers success/error/malformed/
  traceparent). The uncovered lines are one-line method bodies; they are
  exercised for real by `smoke` (health→login→products→purchase→me) and by
  every `apps/web` feature test that calls them through react-query. Adding 80
  near-identical unit assertions would be snapshot-grade noise, so they are left
  to the integration/e2e path.
- **`adapters/db/seed.ts`, `reseed.ts`, `migrate.ts`** — dev/data-loading
  entry scripts run by `db:seed` / `db:reseed` / `db:migrate` and exercised by
  `smoke`; they are not port implementations and are not meaningfully
  unit-testable, so they are excluded from the measured adapter surface (see the
  coverage exclude list). Their SQL twins (`price-migration`,
  `access-items-migration`, `discussion-author-display-migration`) ARE
  unit-tested via their TypeScript transforms.
- **`adapters/db/repositories.ts`** — real SQL; the parts that carry logic
  (search prefix, importer joins, grant windows) are covered by the DB-backed
  adapter tests and e2e; pure-CRUD passthroughs are validated by `smoke`.

## Tests added by this audit

Focused on the highest-risk exported logic that had no direct unit assertion:

- **Money / price math** — `core/domain/commerce.test.ts`: `graceExpiresAt`,
  `nextPeriodEnd` (month/year, month-end overflow), the recurring-needs-interval
  refinement on both price schemas, order-list/export query defaults and caps.
- **Error taxonomy exhaustiveness** — `core/contract/http-status.test.ts`:
  every `ERROR_CODES` member maps to an HTTP status and a CLI exit code; auth
  failures share exit 3 by design; integration failures get distinct 5xx/412.
- **Envelope contract** — `core/contract/envelope.test.ts`: `toEnvelope`,
  strict and loose envelope schemas.
- **CLI exit codes** — `apps/cli/src/output.test.ts`: `emit` prints exactly one
  JSON envelope (agent contract), routes human errors to stderr, and sets the
  correct `process.exitCode` for every error kind.
- **Tenant-secret isolation & error mapping** —
  `adapters/crypto/tenant-secret-resolver.test.ts`: per-tenant lookup (no
  cross-tenant leak), not_found when unconfigured, decryption failure
  propagated rather than swallowed.
- **API-key crypto** — `adapters/auth/api-key-crypto.test.ts`: URL-safe secret
  generation, uniqueness, deterministic SHA-256 hashing for by-hash lookups.
- **Tenant settings partial-update** — `core/domain/tenant.test.ts`:
  omit-keeps / empty-string-and-null-clear semantics, URL validation.
- **Domain Result combinators** — `core/domain/result.test.ts`.
- **Subscription lifecycle math** — `core/server/usecases/subscription-lifecycle.test.ts`:
  start/renew/fail/provider-update, including the price-missing fallbacks
  (zero amount, PLN, monthly), grace-buffered grants, and cancel mapping.
- **Simulated-cycle error paths** — added to
  `core/server/usecases/stripe-webhook.test.ts`: unknown subscription,
  missing provider id, already-canceled.
- **Course-management guards** — extended
  `core/server/usecases/course-management.test.ts` with the validation /
  not-found / partial-update-fallback branches across create/update/attach/
  detach.
- **Orders CSV export** — extended `core/server/usecases/orders.test.ts` with
  spreadsheet-formula neutralization, quoting, the slug-less filename
  fallback, and invalid-query rejection.
- **Auth e2e transport** — `adapters/auth/e2e-http.test.ts`: origin/CSRF header,
  bearer-token attachment, and JSON-parse failure handling.
- **Repository SQL against a real database** —
  `adapters/db/repositories.test.ts`: an isolated-Postgres integration test that
  seeds two tenants and drives products, members, grants, orders,
  subscriptions, courses, API keys, secrets and the processed-event
  idempotency claim — every read asserts **tenant isolation** (a query for one
  tenant never returns another tenant's rows) and the grant-window active
  filter, revenue-vs-count semantics, and duplicate-claim rejection are
  verified against actual SQL.

Already well covered before this audit (verified, not re-tested): the
subscription lifecycle and grant-window use-cases are exercised end-to-end
through `core/server/usecases/stripe-webhook.test.ts` (checkout → subscription +
grace grant, invoice.paid renewal, payment_failed → past_due, cancel, and the
simulate-cycle / simulate-failure paths), and `grants.test.ts` covers
create/renew/revoke plus tenant-isolation negatives.

## Ratchet — how it works and how to raise floors

- `coverage-baseline.json` (at `app/coverage-baseline.json`) stores a per-layer
  floor for lines/branches/functions, each **rounded down** from the achieved
  number.
- `scripts/coverage-check.ts` (`npm run coverage:check`) compares the latest
  `coverage-summary.json` against those floors and **fails** if any layer drops
  below any floor. It is part of `npm run coverage` but intentionally **not**
  part of `npm run check` — the static gate stays fast and the coverage gate is
  opt-in / CI-friendly.
- **To raise a floor** after adding tests: run `npm run coverage:baseline`,
  which re-measures and rewrites the floors to the new (rounded-down) achieved
  numbers. Commit the updated `coverage-baseline.json`. Never hand-raise a floor
  above what `npm run coverage` currently reports, or the gate will fail on a
  clean tree.
